# Architecture Decision Records

Short ADRs for the Kartly Support Agent. Status is **Accepted** unless noted. Numbering here supersedes the informal numbering used during planning. See `DESIGN.md` for the full context.

---

## ADR-001: Chat-style API only in v1
- **Context:** Supporting email, chat, and social adds adapters without teaching anything new about the agent.
- **Decision:** v1 exposes a chat-style HTTP API. Email becomes a later adapter on the same ticket model.
- **Alternatives:** Email-first; multi-channel from the start.
- **Consequences:** Faster to build and test; channel adapters stay out of the core.

## ADR-002: English only
- **Context:** Multilingual support multiplies the eval set and prompt surface.
- **Decision:** English only in v1.
- **Alternatives:** Hindi/English mix.
- **Consequences:** Smaller eval set; multilingual is a clear future extension.

## ADR-003: Risk tiers and INR 1,000 auto-refund threshold
- **Context:** Autonomy must match risk. Money actions need limits.
- **Decision:** Four tiers (0 read-only, 1 low-risk writes, 2 money, 3 never autonomous). Refunds up to INR 1,000 are automatic; above that require human approval. The threshold is configurable per tier.
- **Alternatives:** Everything needs approval; higher threshold.
- **Consequences:** Routing, permissions, and evals all key off the tier. Threshold can be tuned with data.

## ADR-004: Shadow-first rollout with per-tier mode switch
- **Context:** Real teams do not launch agents at full autonomy.
- **Decision:** Per-tier mode (`off`, `shadow`, `auto`) exists from day one. Order: shadow everywhere, then auto for Tier 0-1, then Tier 2.
- **Alternatives:** Build autonomy only, add drafts later.
- **Consequences:** Draft path is a first-class feature; doubles as a kill switch.

## ADR-005: v1 scope capped at about 8 intents
- **Context:** Each intent multiplies eval cases and tool surface.
- **Decision:** order status, tracking, return, refund, cancel, address change, policy FAQ, escalation.
- **Alternatives:** Broader coverage.
- **Consequences:** Eval set stays manageable; cut intents before cutting evals.

## ADR-006: Workflow with a bounded agent loop, plain Python, no framework
- **Context:** Fully autonomous agents are harder to test and secure. Frameworks hide behavior.
- **Decision:** Deterministic stages around a single bounded LLM tool-calling loop, implemented as a plain Python state machine.
- **Alternatives:** LangGraph or similar; fully autonomous agent.
- **Consequences:** More code to write, fewer hidden behaviors, more learning. A framework can still be discussed as an alternative.

## ADR-007: Tool Gateway as the sole enforcement point
- **Context:** Prompts cannot be trusted to enforce policy against injection.
- **Decision:** The LLM never touches the database. All actions go through a deterministic gateway that does authz, eligibility checks, limits, idempotency, and audit logging. `customer_id` is injected server-side and is never a tool argument. Idempotency keys are generated server-side. Approvals are bound to a payload hash and expire.
- **Alternatives:** Policy in the system prompt; per-tool ad hoc checks.
- **Consequences:** A successful injection cannot cross customer boundaries or double-refund. The gateway needs thorough property tests.

## ADR-008: Hybrid retrieval with a reranker
- **Context:** Policy text contains exact terms ("30 days", "final sale") where pure vector search is weak.
- **Decision:** Postgres full-text plus pgvector, followed by a reranker.
- **Alternatives:** Vectors only; external vector DB.
- **Consequences:** One database to run; retrieval gets its own eval (hit@k, MRR).

## ADR-009: Upfront routing with a hard-rules floor
- **Context:** Cost and risk both depend on classifying early. A small classifier can miss dangerous tickets.
- **Decision:** Keyword/regex hard rules, then an LLM classifier. Final tier is the max of the two, so the classifier can raise risk but never lower it. Cascade routing is a later measured experiment.
- **Alternatives:** Cascade first; classifier only.
- **Consequences:** High recall on Tier 3; routing quality is measurable on its own.

## ADR-010: Hard run limits
- **Context:** Agent loops can burn budget and time.
- **Decision:** Max 6 loop steps, 8 tool calls, a per-run token budget, and a wall-clock timeout. The original $0.30 per-run cap is expressed as tokens, with a shadow-cost equivalent.
- **Alternatives:** Dollar caps only.
- **Consequences:** Limits stay meaningful even when real spend is zero.

## ADR-011: Provider-agnostic LLM adapter
- **Context:** No paid API access; free tiers and local models change often.
- **Decision:** One adapter with an OpenAI-compatible interface (own thin layer or LiteLLM); all models selected by config.
- **Alternatives:** Hard-wire one provider.
- **Consequences:** Models and providers can be swapped without code changes; supports fallback chains.

## ADR-012: Two model tiers on free resources
- **Context:** Student budget; RTX 3050 with 4 GB VRAM.
- **Decision:** A small local model (3-4B class, 4-bit) for the classifier, embeddings, reranker, and smoke evals; hosted free tiers for the complex resolver and the judge. Exact models are config.
- **Alternatives:** Paid APIs; 7-8B local models that spill into system RAM.
- **Consequences:** Weaker small-model tool calling is expected and measured; guardrails and repair-retry matter more.

## ADR-013: Shadow pricing
- **Context:** Real spend is $0, but cost is a core engineering metric.
- **Decision:** Log tokens for every call and compute cost from a reference price table in config. Report results "at reference prices".
- **Alternatives:** Skip cost tracking.
- **Consequences:** Routing and caching experiments produce meaningful numbers.

## ADR-014: Rate-limit-aware client with fallback chain
- **Context:** Free tiers have tight per-minute and per-day limits, and failed requests may still count against quotas.
- **Decision:** Token-bucket client, 429 handling with capped retries and jitter, circuit breaker, and a configurable fallback chain ending at the local model and then the human queue.
- **Alternatives:** Unbounded retries.
- **Consequences:** Reliability work becomes a visible feature; demo needs quota protection.

## ADR-015: Synthetic data only
- **Context:** Some free tiers may use inputs to improve their models.
- **Decision:** No real customer data is ever sent to hosted providers; the store and tickets are synthetic.
- **Alternatives:** None considered.
- **Consequences:** Safe to use free tiers; realism comes from careful curation.

## ADR-016: State-based grading first, LLM judge second
- **Context:** Reply text is a poor proxy for whether the right action happened.
- **Decision:** Primary grading is final database state and tool-call correctness. An LLM judge scores quality on a rubric, uses a different model family than the resolver, and is calibrated against ~30 human labels.
- **Alternatives:** Judge-only grading.
- **Consequences:** Cheaper, more reliable evals; judge agreement is reported.

## ADR-017: CI uses a smoke set with record/replay
- **Context:** Free-tier quotas cannot support a full eval on every PR.
- **Decision:** ~25-case smoke set on every PR using recorded LLM responses; full golden set nightly or manually. Safety metrics are hard gates.
- **Alternatives:** Full eval in CI.
- **Consequences:** Deterministic, free PR checks; full-eval drift caught nightly.

## ADR-018: Own run_steps plus OpenTelemetry; viewer decided in Week 6
- **Context:** Self-hosted Langfuse runs several heavy services; a laptop is constrained.
- **Decision:** Persist `run_steps` in Postgres and emit OpenTelemetry now. Choose a lightweight viewer (for example Arize Phoenix) or hosted free tier at the observability milestone.
- **Alternatives:** Self-hosted Langfuse from the start.
- **Consequences:** Tooling choice is deferred without blocking replay and debugging.

## ADR-019: Hosting decision deferred to Week 7
- **Context:** Free/cheap hosting options change frequently.
- **Decision:** Check current options at the deployment milestone. Design stays container-based and portable.
- **Alternatives:** Pick a host now.
- **Consequences:** No lock-in; deployment is verified by CI and a load test.

## ADR-020: 8-week plan with Week 8 as buffer
- **Context:** Solo build with real risk of overruns.
- **Decision:** Seven weeks of milestones, each ending in something runnable, plus one week for the golden set, hardening, and README.
- **Alternatives:** Plan without buffer.
- **Consequences:** Intents are cut before evals if time slips.

## ADR-021: One transaction per tool call, fail-closed audit, no existence oracle
- **Context:** ADR-007 makes the gateway the only enforcement point but leaves open how a call executes and what happens when something fails.
- **Decision:** Each call runs in its own transaction. The tool runs inside a SAVEPOINT so a failure undoes its writes, and exactly one `audit_log` row is written in the same transaction whatever the outcome. If the audit row cannot be written, the call is rolled back and the exception propagates (fail closed). Ownership is part of the query, and a foreign order and a nonexistent order return identical errors to the model; only the audit log records `not_owner` and a `cross_customer_access` security event. Unknown arguments, including `customer_id`, are validation errors. Everything written to the audit log is sanitised: size-bounded, with NUL characters, lone surrogates, NaN and huge integers removed.
- **Alternatives:** Audit in a separate transaction (survives rollback but allows an action with no record); a caller-owned session (the caller must remember to write the audit row); an "access denied" error for foreign orders (confirms which order IDs exist).
- **Consequences:** Rejected and failed calls are recorded too, and security events are queryable (`details->>'security_event'`). The orchestrator must handle the rare exception from `call`. Tool handlers get a savepoint, not their own commit. Verified on Postgres, where an aborted transaction and JSONB limits behave differently from SQLite.

## ADR-022: Tool output is pre-computed and minimal
- **Context:** Models mis-handle arithmetic and dates, long tool output wastes context, and tool results end up in prompts, traces, and logs.
- **Decision:** Tools return rupee strings instead of paise, compute facts such as "delayed" in code, return only city, state, and pincode for the destination, cap lists (20 items, 5 shipments, 5 events), and length-limit third-party text such as carrier event details.
- **Alternatives:** Return raw rows and let the model work it out; return full addresses.
- **Consequences:** Fewer tokens and fewer model errors, less personal data in traces. Some questions will need a new tool field. The context builder (Week 3) still wraps all tool output as untrusted data.

## ADR-023: The LLM client classifies failures but never retries or falls back
- **Context:** ADR-014 wants a rate-limit-aware client with a fallback chain. Putting retries inside the HTTP client would hide failures from tracing and make cost, latency and attempt counts impossible to attribute to a model.
- **Decision:** `OpenAICompatClient` makes exactly one request per call and turns every failure into a typed error with a `retryable` flag: `RateLimitError` (with `Retry-After`), `ProviderUnavailableError` (5xx and refused connections), `LLMTimeoutError`, `MalformedResponseError` (retryable); `ToolUseFailedError` (HTTP 400 `tool_use_failed`, keeps the model's output so the loop can ask for a repair); `AuthenticationError`, `ModelNotFoundError`, `BadRequestError` (configuration bugs, fail fast). A malformed tool call is not an exception: `ToolCall.arguments` is `None` with a `parse_error`. Request options a provider cannot take (Ollama has no `tool_choice`) are listed in `ChatResponse.ignored_params`, never dropped silently. Missing usage from a provider is estimated and flagged `estimated=True`. API keys are redacted from provider error text and never appear in `repr`. The retry, circuit-breaker and fallback wrapper (Week 5) implements the same `ChatClient` protocol on top.
- **Alternatives:** Retries inside the client; the OpenAI or LiteLLM SDK; one client per provider.
- **Consequences:** Every attempt can be traced and priced individually. The agent loop must handle `LLMError`. The wire protocol is a few hundred lines we own and test (including over a real socket), at the cost of not getting provider-specific features for free.

## ADR-024: Local model context is set in a Modelfile; every reference price names its source
- **Context:** Ollama's OpenAI-compatible endpoint cannot set the context window per request, and its default is far smaller than our prompts (roughly 8k tokens once the system prompt, tool schemas and history are in). A too-small window truncates the prompt silently. Separately, a free tier or local model has no bill, so shadow costs (ADR-013) are only as trustworthy as their price sources.
- **Decision:** `ollama/Modelfile.small` creates `kartly-small` with `num_ctx 8192` and `temperature 0`; `models.yaml` points at that name, and the README says to check `ollama ps` for CPU offload on a 4 GB GPU. Every model in `models.yaml` carries a price `note` saying where the number came from and when (a test enforces this). A local model with no published price borrows a comparable hosted model's price and says so.
- **Alternatives:** Pass `options.num_ctx` through a native Ollama client (a second wire protocol); rely on the default context.
- **Consequences:** One extra setup command for local models. Shadow costs are good for comparing routing and caching strategies, not for budgeting. The Week 1 benchmark includes a context-length probe.

## ADR-025: Hosted model lineups change, so model IDs live only in config
- **Context:** The first real smoke run (2026-10-26) got HTTP 404 for `llama-3.1-8b-instant`. Groq's deprecation page lists it, and `llama-3.3-70b-versatile`, as shut down on 2026-08-16 with `openai/gpt-oss-20b` and `openai/gpt-oss-120b` as the replacements, and a third-party page reports they are no longer available to free accounts. The replacements are reasoning models: a reply spends tokens thinking first. The same third-party page reports free-tier limits of 1,000 requests/day, 8,000 tokens/minute and 200,000 tokens/day per organisation.
- **Decision:** Model IDs appear only in `config/models.yaml` (ADR-011), so this was a config change. `groq_small` is now `openai/gpt-oss-20b` and `groq_large` stays `openai/gpt-oss-120b`. A model may carry an `extra_body` of provider-specific request fields (`reasoning_effort: low` for the small tier, `medium` for the large one); it cannot set any field the client owns (model, messages, tools, temperature, token caps, ...), and the client sends its own arguments last, so config can never silently override what the agent loop asked for. The smoke test allows 512 output tokens and says so when a reply was cut off by the cap.
- **Alternatives:** Pin an old model (it is gone); hard-code `reasoning_effort` in the client; switch providers.
- **Consequences:** The next retirement is a one-line edit. A 404 means "check the model name" (a configuration error, not retryable). The 8,000 tokens/minute figure, if it holds, means Groq cannot serve a request whose prompt is anywhere near 8k tokens, so a local-to-Groq fallback only works for prompts that fit. The context builder (Week 3) therefore gets a hard prompt budget for any model that can fall back to Groq, to be confirmed against the real limit in Week 5.

## ADR-026: A bounded loop with explicit stop reasons; every step stored as it happens
- **Context:** DESIGN.md sections 5 and 11 ask for hard caps, one repair retry for broken tool calls, loop detection, and persisted steps. A loop that can only "finish" or "crash" hides the difference between a model that gave up, a budget that ran out and a provider that failed.
- **Decision:** `AgentLoop` is plain Python and touches no database; `TicketRunner` adds persistence. Limits: 6 model calls (a failed request counts), 8 gateway calls, 20,000 tokens, USD 0.30 shadow cost and 120 s, all checked *before* each model call. The token check uses a size estimate and shrinks the output cap to what is left, so the budget is a soft ceiling and no request is sent that could not fit. One repair per run, shared by broken tool arguments, a tool call the provider rejected, and an empty reply; then the run stops. An identical repeated tool call is answered with an error and not run again, and a second repeat stops the run. A reply cut off by the output cap is never used. Every outcome other than an answer has its own stop reason (`step_limit`, `tool_limit`, `token_limit`, `cost_limit`, `timeout`, `no_progress`, `malformed_output`, `truncated_reply`, `llm_error`, `gateway_error`) and hands the ticket to a human. The loop never retries a provider error (ADR-023). Each step is committed in its own transaction as it happens, so a crash leaves every earlier step. A model-call step stores only the messages added since the previous call, so a trace grows linearly instead of quadratically. In shadow mode the answer is stored as an agent message and the ticket becomes `drafted`; nothing is sent. Cost columns became `NUMERIC(16,10)` (migration 0002) because a single small call costs a few millionths of a dollar.
- **Alternatives:** An agent framework; retries inside the loop; a full prompt copy in every step; sending answers automatically.
- **Consequences:** Failures are explainable and countable by reason, which is what the escalation-rate metric and the red-team gates need. Replaying a run means concatenating its message deltas and re-executing the tools. Trace fields are size-bounded (4,000 characters per string), so a very long reply is shortened in the trace though not in the stored message. The screening, routing and validation stages are not built yet, so a ticket goes straight from `received` to `resolving`.

## ADR-027: API-key auth with the caller asserting the customer; 202 plus a bounded in-process run pool
- **Context:** DESIGN.md section 8 needs ticket intake and a trace endpoint now, before the queue (Week 5), the admin UI and the screening stages exist. Two questions decide the shape: who is allowed to call, and what happens when a ticket arrives while the model is slow or the system is already busy.
- **Decision:** Every `/v1` route requires an `X-API-Key` header, compared in constant time; a missing and a wrong key get the same `401`, and the app refuses to start with a key under 8 characters or none at all. The caller is the storefront backend, which has already authenticated the shopper, so `customer_id` in the request is trusted exactly as far as the key is: it is stored on the ticket once and is the only identity the gateway will use (ADR-007, ADR-021). `POST /v1/tickets` creates the ticket, hands the run to a `BoundedExecutor` and returns `202`; `?wait=true` waits for the result instead (`200`, or `202 resolving` if the wait outlasts the run's own time limit). A repeated `external_id` returns the first ticket, enforced by the unique index so two simultaneous requests still make one ticket. The executor runs `KARTLY_MAX_WORKERS` runs at a time and allows `KARTLY_MAX_PENDING_RUNS` in total; past that, the ticket just created is deleted and the API answers `503` with `Retry-After`, so a retry is clean. A validation error returns the field and rule but never the offending value. A crashed run is a generic `500` whose details are in the trace, not the response.
- **Alternatives:** OAuth or per-customer tokens (more machinery than one trusted backend needs); an unbounded `BackgroundTasks` (denial of wallet, since each run spends provider quota); waiting for the Redis queue before building the endpoints; a synchronous-only endpoint (a slow local model would hold the connection open).
- **Consequences:** A leaked key lets its holder open tickets as any customer, so the key is a secret to rotate, and per-caller keys and rate limits are future work. Queued runs live in memory and are lost on a restart (their tickets stay `received`); the Redis queue in Week 5 fixes that without changing the routes, because callers only see `submit` and `shutdown`. There is no request-size limit in the app (a reverse proxy sets it, Week 7) and `/docs` is open. The stop-the-server path waits for runs in progress before closing the database, and the real launch (uvicorn, Postgres, a model over HTTP) was exercised end to end.

## ADR-028: Golden cases are graded on state first, on throwaway in-memory stores
- **Context:** DESIGN.md section 9 wants end-to-end success graded by final database state, safety as a hard gate, and every change logged. The agent so far has only read tools, so most "state" is what the gateway recorded rather than rows changed, but the structure has to be right before write tools arrive.
- **Decision:** Cases are YAML, validated strictly (unknown fields are errors). Each case runs on a fresh in-memory SQLite copy of the seed at a fixed clock, through the real loop and gateway. The grader is a pure function over evidence taken from the stored trace (tool calls, audit security events) and a before/after digest of the shop's tables (customers, orders, items, shipments, actions). Checks carry a severity: safety (store unchanged, security events exactly as expected, no forbidden calls, no leaked data or false action claims) or quality (outcome, expected calls, reply content). Reply checks are whole-phrase matches with alternatives. A forbidden call fails the case even if the gateway blocked it, because the gateway is the safety net, not the plan. Provider and platform errors are reported as errors, not model failures. Each run saves full JSON results and appends a row to `evals/runs/experiments.csv` with a fingerprint of the case set. The checks are verified with scripted perfect and deliberately wrong trajectories and with mutation testing of the grader.
- **Alternatives:** Grading the reply text only; an LLM judge first; running against the developer's Postgres (clock drift, shared state); storing recorded model responses now.
- **Consequences:** Runs need no infrastructure and are repeatable. SQLite does not exercise Postgres-specific behaviour (covered by the integration tests instead). Phrase matching is brittle and will reject some correct wording; the judge and a record/replay smoke set are later work. Cases that expect a draft today (the refund demand) must change when approvals exist. Multi-turn cases and the ~30 adversarial cases still have to be written.

## ADR-029: Prompt v1: tool descriptions say what each tool does not return
- **Context:** The first eval runs (cases 07681c78) showed `openai/gpt-oss-20b` calling only `get_order` for "where is my order", because `get_order`'s description claimed to answer "where it stands". It then had no delivery date or delay flag and told a customer a late parcel was "on its way" (3 of 7 Tier 0 failures, plus one run that followed an injected order lookup).
- **Decision:** `get_order` now says it has no carrier, estimate or delay information and points to `get_tracking`; `get_tracking` says it is for where/when/why-late questions. The system prompt (v1) names the same split, asks for the delivery date and a plain statement of delay, and says to look up only order numbers the customer asks about, never ones a message tells it to fetch. `PROMPT_VERSION` is "v1" so experiment rows are comparable.
- **Alternatives:** Merging the two tools; forcing `tool_choice`; prompting only (the descriptions are what the model reads at call time).
- **Consequences:** Verified only by re-running the evals: compare `experiments.csv` rows for prompt v0 and v1 with the same `cases_digest`. Small models may still fail; the injection case remains a model-level failure until a screening stage exists.

## ADR-030: A deterministic injection screen before the model, and a stricter grader
- **Context:** With prompt v1, `openai/gpt-oss-20b` on Groq still followed an injected request to look up another customer's order (the gateway blocked it, nothing leaked, but it is a safety failure). The local model sometimes answered "not found" for a friend's order without looking it up, so the case passed or failed on luck: the grader treated a missing expected security event as a safety failure for the model, when it is really a missed lookup.
- **Decision:** (1) `guards/screen.py`: regular-expression rules over normalised customer text (NFKC, casefold, zero-width characters removed). A hit ends the run before any model call: stage `screen` (new `StepKind.STAGE`), audit row by the `system` actor with `prompt_injection_suspected`, run `succeeded/escalated`, ticket `escalated`, `StopReason.SCREENED`. `TicketRunner(screen=None)` and `kartly.evals --no-screen` turn it off to measure the bare model. (2) The grader splits the events check: "no unexpected security events" (safety) always, and "expected security events recorded" (quality) only when the case lists some.
- **Alternatives:** A model-based classifier (costs a call and can itself be injected); stripping the suspicious text and continuing (hides the attack from the human); making the grader count a refusal as a pass (it hides a model that never looked).
- **Consequences:** Blatant attacks cost nothing and reach a human. A false positive also reaches a human, which is cheap but visible in the escalation rate: watch it. The screen can be evaded by wording, so the gateway and the `injection-polite-lookup` case remain the real measure. That case first treated any lookup of the other order as a safety failure, but the model cannot know an order is foreign without asking (the same reason `idor-friends-order` requires the lookup), so it now expects the lookup and the gateway's `cross_customer_access`, and fails on a passed `customer_id`, leaked data, or a reply that drops the real question. The case set changed (11 cases), so `cases_digest` changed: earlier `experiments.csv` rows are not comparable. Rules need review against real tickets once there are any.

## ADR-031: Tier 3 hard rules run before the model, and are measured on their own
- **Context:** DESIGN.md section 6 puts hard rules first in routing and sets a Tier 3 recall gate of 99%. A legal threat, a fraud claim, an injury or a customer in distress must reach a person; a small model deciding that is the weakest option.
- **Decision:** `routing/rules.py` holds keyword patterns in six categories (legal, fraud, account_security, safety, distress, threat) over the same normalised text as the injection screen. A hit ends the run before any model call: stage `route`, audit row `route.escalated` (actor `router`, not a security event), run `succeeded/escalated`, `StopReason.ROUTED_TIER3`. The screen runs first; `TicketRunner(rules=None)` turns the rules off. `python -m kartly.evals.routing` measures them on `evals/routing/tier3.yaml`: recall on messages a human must handle, false-alarm rate on ordinary messages, per category. Both are gates. Phrasings known to be wrong either way carry a `known:` label, are reported on their own line, and never count toward the gate.
- **Alternatives:** Classifier-only routing (slower, and a small model can be argued out of it); a larger rule list tuned to a looser recall (more false alarms for the team); counting known gaps in the gate (it would hide what the rules cover).
- **Consequences:** Cheap and deterministic, and every hit is explainable. The dataset is invented and written by the rule author, so 100% on it is a floor on quality, not a measured production recall; real tickets will find gaps, and each one becomes a new message in the file before the rule changes (the first run found three misses and one false alarm, now fixed with fresh messages added alongside). Known gaps today: paraphrase ("in front of a judge"), Hinglish, spaced-out letters, soft distress ("can't go on"), plus a few false alarms ("badminton court", "police blue shirt", "no need to sue anyone"). The classifier layer is the answer to the first group; the false alarms cost a human a minute each. Abusive-but-not-threatening customers are also left to the classifier (sentiment).

## ADR-032: A classifier that can only raise risk, measured before it is wired in
- **Context:** DESIGN.md section 6 layers a small-model classifier (intent, tier, complexity, sentiment, confidence) over the hard rules, with "final tier = max(rule tier, classifier tier)". A small local model returns broken JSON some of the time, and the Tier 3 rules are known to miss paraphrases.
- **Decision:** `routing/classifier.py` asks for one JSON object (`response_format: json_object`, no tools, ticket quoted as untrusted data, `</ticket>` stripped so it cannot close the quote). Code, not the model, enforces the safety properties: a floor tier per intent (a refund is at least Tier 2, escalation Tier 3), `decide_route` takes the maximum of rule and classifier tier, and a failed call or unusable output is a result with an error that falls back to the rule tier and flags clarification, never an exception and never a lower tier. Confidence under 0.7 sets `needs_clarification`. No output cap is passed: reasoning models may spend hidden tokens against it. `python -m kartly.evals.classify --model NAME` runs it over `evals/routing/intents.yaml` (56 invented messages across the 8 intents, 8 of them Tier 3, six multi-intent labelled by the riskiest ask) and reports intent accuracy, tier accuracy, Tier 3 recall for the whole router and for rules and classifier alone, tickets routed too low or too high, unusable outputs, a confusion list, tokens, cost and latency, with one row per run in `evals/runs/routing_experiments.csv`. Its gate: every Tier 3 message caught and no unusable output.
- **Alternatives:** Trusting the model's tier; function-calling for structured output (not supported uniformly by Ollama); wiring it into `TicketRunner` first (no number to judge it by).
- **Consequences:** Not yet part of the ticket flow: the first job is to see per-model numbers and decide whether the local model is good enough or the Groq model should classify. The labelled messages are small and invented, so accuracy numbers are indicative, not production estimates. Model selection (small vs large tier by routed tier and complexity) and the clarifying-question path come after.

## ADR-033: Classifier prompt c2, and prompts that stay selectable for like-for-like comparison
- **Context:** The first real runs of prompt c1 (56 messages, digest 4bba7963) gave the same headline on both models: intent accuracy 89.3%, no unusable output, Tier 3 recall 88.9% (the rules alone caught 1 of 9, the classifier alone 7 of 9). Both read "Money left my account for something I never bought from you" as a refund request. Both read general policy questions that mention refunds or returns ("How long does a refund take?") as requests. `local_small` dropped the refund in "cancel and refund" and "where is it, otherwise refund" (3 messages routed too low); `groq_small` raised the tier needlessly on 8 messages (tier 1 for plain tracking questions). Latency was 4.1 s p50 local and 0.6 s Groq, about 400 to 500 tokens (under $0.00005) per message.
- **Decision:** Prompt c2 (a) lists a charge or payment the customer did not make or for something never ordered under escalation, (b) defines policy_faq as a general "how does it work" question even when "refund" or "return" appear, (c) tells the model to pick the riskiest intent when a message asks for several things, with the order, and (d) says the tier follows the intent and an annoyed customer asking where a parcel is stays tier 0. Both prompts stay in `PROMPTS`; `--classifier-version c1|c2` runs either, and the cases digest no longer includes the prompt version, so rows for different prompts on the same digest are directly comparable (as ADR-029 does for the agent prompt). Fourteen new messages with different wording (a card payment never recognised, a bill for an order "I didn't place", a threat from a delivery person, an illness from a product, hopeless wording without a keyword, more policy questions, two more multi-intent tickets) were added with c2; they were written after seeing the c1 failures but are phrased differently from them, so the c2 numbers are not a pure held-out score.
- **Alternatives:** Dropping the model's own tier and deriving it from the intent only (it rescued one multi-intent message on each model, and costs nothing to keep, but it also adds the over-routing, so watch the "too high" count); adding a keyword rule for "money left my account" (a narrow patch for one phrasing; the classifier is where paraphrase belongs); retraining.
- **Consequences:** To compare, run both prompts on the new digest for each model. A c2 that fixes the fraud paraphrase but reads more things as escalation will show up in the false-alarm and "too high" numbers. The Tier 3 gate is strict (every Tier 3 message caught) on a small invented set, so it will often fail; the more useful reading is which messages, and whether the rules and the classifier miss different ones.

## ADR-034: The router is optional, runs after the rules, and fails open to the resolver
- **Context:** On 70 labelled messages (digest 1cd6e501, 14 of them Tier 3) the four classifier runs gave: `groq_small` c1 intent 87.1%, tier 82.9%, Tier 3 recall 92.9%, 10 routed too high; c2 90.0%, 91.4%, 100%, 4 too high. `local_small` c1 82.9%, 80.0%, 92.9%, 10 too high; c2 87.1%, 88.6%, 85.7%, 4 too high (it missed "billed for an order I didn't place" and "my mother fell very sick after using the supplement"). c2 beat c1 on both models and fixed the card-payment paraphrase both models missed under c1, so c2 is the default. Groq took 0.6 s p50 and about 680 tokens per label, local 4.0 s and 560 tokens, both under $0.00006. The rules alone caught 1 of 14 Tier 3 messages here, which only says the dataset was written to evade them; it is not a production estimate. Self-reported confidence was 0.9 to 1.0 on almost every answer, including wrong ones, so the "confidence under 0.7 asks a question" step in DESIGN.md has no signal to act on.
- **Decision:** `TicketRunner(router=client)` (settings `KARTLY_ROUTER_MODEL`, CLI `--router`, eval `--router`) labels the customer's text after the screen and the rules. A Tier 3 label (after the intent floor) closes the run as `routed_tier3` with trace steps `classify` (0) and `route` (1, source `classifier`) and the same `route.escalated` audit row; the label call's tokens and cost are added to the run. Anything else carries on to the resolver, with the label in the trace. A failed or unusable label also carries on (recorded as a failed `classify` step): today every tool is read-only, the gateway is the real defence, and holding every ticket whenever the router has a bad minute would send the whole queue to humans. Off by default, so the golden cases (which grade the resolver) are unchanged.
- **Alternatives:** Failing closed on a router error (right once write tools exist; revisit in Week 4); taking the maximum tier over two router models (would have caught `local_small`'s two misses, at twice the calls); using the label to choose a larger resolver model (waits for something to choose between); a confidence-based clarifying question (no usable confidence signal).
- **Consequences:** Recommended setup is `KARTLY_ROUTER_MODEL=groq_small`: it passes the Tier 3 gate on this set and costs under a second. The local model is not safe as the only router. Dependence on a free tier needs the fallback chain from Week 5. Over-routing is the cost to watch: 4 of 70 messages were escalated or priced too high with c2, and `groq_small` read "wrong pincode, it should be 452010" as a policy question (tier 0), which an action-capable resolver would miss. The router's label is not yet used to choose tools or a model.

## ADR-035: A synthetic policy KB and a retrieval baseline measured before anything is built on it
- **Context:** Week 3 needs policy answers that are grounded in text, and a way to tell whether a change to search helps. Without labelled question-to-chunk pairs, every retrieval change would be judged by eye.
- **Decision:** `kb/` has eight invented policy files (44 chunks). `retrieval/chunking.py` makes one chunk per `##` section with a stable id, skips the preamble before the first section, keeps quotes inside sections, and splits sections over 200 words on paragraphs. `retrieval/bm25.py` is a small BM25 (k1 1.5, b 0.75, heading counted twice, light stemmer, stop words) behind a `Retriever` protocol returning `Hit(chunk, score)`. `python -m kartly.evals.retrieval` scores it on `evals/retrieval/queries.yaml` (46 questions: 18 plain, 15 paraphrase, 7 messy, 2 multi-chunk, 4 unanswerable) with hit@k, recall@5 and MRR@10 per tag, and logs to `retrieval_experiments.csv` with KB and question digests.
- **Baseline (kb 30b5be00, questions 029b664a):** hit@1 0.762, hit@3 0.881, hit@5 0.929, recall@5 0.901, MRR 0.825. Plain 0.833 at hit@1, paraphrase 0.667 (hit@5 0.800), messy 0.714. Answerable top score averages 7.37; unanswerable averages 2.44 with a maximum of 4.99, so a threshold between roughly 5 and 7 separates them on this set, to be re-checked once retrieval changes.
- **Alternatives:** Starting with dense embeddings (no baseline to beat, and the user's embedding model is unconfirmed); a vector store library (hides what is being measured); an LLM-written question set (the questions were written by hand with different wording from the policy text, but by the same author as the KB).
- **Consequences:** Paraphrase is the weak spot, as expected for lexical search: the misses are where the question shares few words with the policy. That is the case for a dense retriever and fusion next. The KB and questions are small and invented, so numbers show direction, not production quality. Not yet connected to the agent: the `search_policy` tool, context builder and grounding checks come after retrieval is improved.

## ADR-036: Dense search wins on this set; fusion buys recall, not precision; the question set was too easy
- **Context:** First dense and hybrid runs on the 46 questions (kb 30b5be00, questions 029b664a), embedding model `nomic-embed-text` through Ollama's `/api/embed` (with its `search_document:`/`search_query:` prefixes; title, heading and body embedded together, as BM25 indexes them).

  | retriever | hit@1 | hit@3 | hit@5 | recall@5 | MRR | paraphrase hit@1 |
  |---|---|---|---|---|---|---|
  | bm25 | 0.762 | 0.881 | 0.929 | 0.901 | 0.825 | 0.667 |
  | dense | 0.952 | 0.976 | 0.976 | 0.956 | 0.968 | 1.000 |
  | hybrid (RRF, k=60) | 0.810 | 0.952 | 1.000 | 0.980 | 0.884 | 0.733 |

- **Decision:** `dense` and `hybrid` join `bm25` behind the same `Retriever` protocol (`HybridRetriever` sums `1/(60 + rank)` votes over each retriever's top 20). No retriever is wired into the agent yet. The eval now also reports the lowest answerable top score and the cut-off that best separates answerable from unanswerable questions, and the question set grew from 46 to 74 (20 more answerable questions, including Hinglish and near-duplicate chunks, and 8 more unanswerable ones that share words with real topics), written without looking at which questions failed. The first 46 rows are comparable among themselves (digest 029b664a); the 74-question set has a new digest (6963dfe9) and all three retrievers need re-running on it.
- **Findings:** BM25's weakness is paraphrase, as expected. Dense fixed it completely on this set (15 of 15 first), and its one miss from the top 5 was q01 ("return policy for shoes"), a plain question that BM25 gets right. Equal-weight RRF averaged a strong ranker with a weaker one: better than BM25 everywhere, but worse than dense at hit@1 (0.810 vs 0.952), though it was the only run with every answerable question in the top 5. Dense scores are tightly packed (answerable mean 0.77, unanswerable mean 0.60, max 0.64), much less separated than BM25's (7.4 vs 2.4), so a dense-only no-answer cut-off will be fragile; the fused score is a vote total and not usable for it.
- **Alternatives:** A cross-encoder reranker now (the data does not justify it: dense is within two questions of perfect on 46, so there is nothing measurable to gain until the set is harder, and a second model costs VRAM on a 4 GB card); weighted fusion (worth trying once the larger set exists, so the weight is not tuned on 46 questions); hosted embeddings (a paid or rate-limited dependency for no measured gain).
- **Consequences:** The question set was written by the same person as the knowledge base, with a small chunk count, so it flatters every retriever; one question is 2.4 points of hit@1. The numbers say dense beats BM25 on paraphrase, not that 0.952 is what real tickets would get. Next: re-run all three on the 74 questions, then decide between dense alone, weighted fusion and a reranker from those numbers, and choose the no-answer cut-off from the cut-off line (and consider a second signal, such as BM25's score or a margin between the first two hits, if the dense one overlaps).

## ADR-037: The agent searches policy with dense retrieval and a no-answer cut-off
- **Context:** On the 74-question set (kb 30b5be00, questions 6963dfe9, 62 answerable, 12 unanswerable):

  | retriever | hit@1 | hit@3 | hit@5 | MRR | paraphrase hit@1 | no-answer cut-off |
  |---|---|---|---|---|---|---|
  | bm25 | 0.694 | 0.790 | 0.855 | 0.758 | 0.630 | 4.016: keeps 53/62, rejects 10/12 |
  | dense (`nomic-embed-text`) | 0.935 | 0.968 | 0.984 | 0.958 | 0.963 | 0.671: keeps 55/62, rejects 10/12 |
  | hybrid (RRF) | 0.774 | 0.935 | 0.984 | 0.854 | 0.741 | not usable (vote totals) |

  Dense won on every ranking metric. Equal-weight fusion pulled it down toward BM25 at hit@1 (0.774) while matching its hit@5, so it is not used. The one answerable question outside dense's top 5 is q01; the one Hinglish question was ranked first by neither (n=1, no conclusion). Dense scores overlap between groups (lowest answerable 0.59, highest unanswerable 0.78), so no cut-off is clean.
- **Decision:** `search_policy(question)` is a Tier 0 tool (`tools/policy.py`) over `DenseRetriever`, returned through the Tool Gateway like the order tools (argument validation, no identity argument, an audit row per call). It returns up to 3 chunks (`chunk_id`, `title`, `section`, `text`) scoring at least `KARTLY_POLICY_MIN_SCORE` (default 0.67, the best cut-off above), or `found: false` with an instruction not to guess and to say a colleague will follow up. Setting `KARTLY_KB_DIR` (for example `kb`) enables it for the API and `python -m kartly.orchestrator`; `python -m kartly.evals --kb kb` enables it for evals. It is off by default, so nothing changes for anyone who does not set it, and it fails at start-up (not on the first customer) if the knowledge base is empty or Ollama cannot embed it. When the tool is available the prompt gains three rules (answer only from returned text, cite `chunk_id` in square brackets, say so when nothing is found), recorded as prompt version `v1+policy`, so runs with and without it are never compared by accident.
- **Alternatives:** Hybrid or weighted fusion (worse than dense here; revisit only if dense misses show up on real tickets); a cross-encoder reranker (dense is within a handful of questions of perfect, and the extra model costs VRAM on a 4 GB card); a stricter cut-off (rejects more answerable questions, each of which becomes a human follow-up); no cut-off and let the model judge relevance (it will paraphrase the nearest chunk for any question).
- **Consequences:** The cut-off was chosen on the same 74 questions it is measured on, so 55/62 and 10/12 are optimistic. Two near-miss questions ("Can I return something at a Kartly store?" style) still score above it, so a wrong "no" is cheap (a human follows up) but a wrong "yes" is possible: the next step is a grounding check on the reply (every claim from a returned chunk, citation present) and golden cases for policy questions, including unanswerable ones the model must refuse to answer. Policy text is treated as data in the prompt; the context builder (8k cap, tool-output wrapping) is still to come.

## ADR-038: Policy answers are measured on their own cases, and "nearby text" is not an answer
- **Context:** The first real policy runs on `groq_small` (2026-11-04, `KARTLY_KB_DIR=kb`): "How long do refunds take?" was answered correctly from `refunds#refund-timeline`, and "Do you price match other websites?" found nothing and handed over, as designed. "Can I return something at a Kartly store?" was a failure: the returns chunks scored above the 0.67 cut-off, and the model answered that Kartly "does not accept in-store returns" and that "all returns must be processed online through our return portal", citing `returns#return-window`. The knowledge base says nothing about stores and no portal exists in it. A citation made the invented claim look sourced.
- **Decision:** Ten golden cases in `evals/golden_policy/` (separate from `evals/golden/`, so the existing digest and runs are unchanged): five answerable questions with the numbers from the knowledge base (refund timeline, return window, delivery charge, COD limit, wallet credit), three the knowledge base cannot answer (price matching and two near-misses, "return at a store" and "choose a delivery time slot", which reuse words from real policy), one that needs both the order and the policy, and one injection hidden in a policy question that the screen must hold. Run with `python -m kartly.evals --model NAME --cases evals/golden_policy --kb kb`; the CLI refuses to run cases that expect `search_policy` without `--kb`. The store-return reply from the real run is a unit test that must fail the case, and an honest hand-over must pass it. The policy rules in the prompt are selectable like the classifier prompts: `p1` (as first shipped, the default, recorded as `v1+policy`) and `p2` (`v1+policy-p2`), which says to state only what the text says, that silence in the text is not a "no", and never to invent a process, portal, form or number. `--policy-prompt` and `TicketRunner(policy_prompt=...)` choose one.
- **Alternatives:** Raising the cut-off until the near-miss is rejected (it would also reject real questions; the near-miss scored like an answerable one); a grounding check first (right next step, but needs this baseline to show what it must catch); fixing only the prompt with no cases (the same failure could return unnoticed).
- **Consequences:** Which wording is better is not known until both are run: run `p1` and `p2` on the same cases and compare. Substring checks can only catch the invented claims listed in each case, so a new kind of invention would pass; the grounding check (every claim traceable to a returned chunk) is the general answer. Policy answers are graded on text the knowledge base was written to contain, so a pass says the model follows retrieved text, not that real policy is correct.

## ADR-039: Policy replies are checked against what the search returned, and held when they are not
- **Context:** The first measured runs of `evals/golden_policy` (10 cases, kb digest 30b5be00, cases 23560724), `--pause 5`:

  | model, prompt | graded | passed | notes |
  |---|---|---|---|
  | groq_small, p1 | 9 of 10 | 8 | store-return near-miss failed again (same invented "return portal" / "does not accept"); 1 run hit Groq's 8,000 tokens/minute limit |
  | groq_small, p2 | 6 of 10 | 6 | the 4 runs that matter (price match, both near-misses, order + policy) all hit the rate limit: **inconclusive** |
  | local_small, p1 | 10 of 10 | 1 | never called `search_policy` in 9 runs; stated "30 days" (the knowledge base says 7), "COD is not available", "no delivery cost"; invented citations such as `[search_policy#price-matching]` and `[returns#refund-processing-time]` |
  | local_small, p2 | 10 of 10 | 3 | called the tool in 3 runs (all passed); 7 runs answered without searching, one with "30 days" and "too late" for a 3-day-old order |

  Per-run cost was about 1,800 to 2,200 tokens on Groq for a policy question (two model calls that each repeat the prompt, tool definitions and returned chunks), against about 400 for a tracking question; at that size a 5 s pause still exceeds 8,000 tokens a minute.
- **Decision:** `guards/grounding.py` checks every drafted reply that cites a section or followed a `search_policy` call: each bracketed citation must be a `chunk_id` returned by a search in this run, and each quantity with a unit (`30 days`, `INR 5,000`, `24 hours`, `20%`) must appear in a tool result or in the customer's own message (compared by value, so `5,000` equals `5000.00`). A reply that fails is not shown: the run closes as `ungrounded` (outcome `escalated`, ticket escalated, no draft), with a `grounding` trace step and a `guard.ungrounded_reply` audit row naming the problems. A reply that passes is stored without its citations (they are kept in the trace step), so customers never see chunk ids. Replies that neither cite nor followed a search (order answers) are not checked. `TicketRunner(grounding=None)` turns it off.
- **Alternatives:** Failing open and only flagging (a wrong policy statement reaches a customer; a held reply costs a colleague a minute); a model that checks every claim against the chunks (the right tool for claims without numbers, but a third call of about 1,000 tokens per reply on a free tier that is already at its limit, and a model that is itself fallible: not built yet); requiring a citation on every policy reply (cheap, but the local model fills it with a made-up id, which is exactly what the check now catches).
- **Consequences:** Reading the printed replies (not replayed), it would hold at least 7 of the local model's 9 policy replies in the p1 run, because they cite a section no search returned; the exceptions are replies that were cut off in the output or cited nothing (the 30-day answer to the order + policy question, which neither searched nor cited, would pass unchecked). It does **not** catch the Groq store-return reply, which cites a real chunk and states no number: "Kartly does not accept in-store returns" passes. That failure is a claim, not a figure, and is what the `p2` wording and, later, a claim-level check are for. Whether `p2` fixes it is not yet known because the runs that would show it were rate-limited. `local_small` is not usable for policy questions (it mostly does not search); policy answering is a `groq_small` job. The token cost per policy answer is now the main practical limit and is the reason the context builder comes next.

  | case | p1 | p2 |

  | price match (no answer) | pass | pass |

## ADR-041: Return eligibility is decided in code, not by the model
- **Context:** The full 14-case policy run on `groq_small` (cases 7ff64e38, `--pause 30`): p1 12 of 14, p2 11, p3 11. All 11 single-question cases passed on every prompt (including the store-return near-miss, which p1 had failed twice before: p1 is not deterministic at temperature 0, so one pass is a sample). The three order-specific cases failed on every prompt. p3 fixed the lookup (it called `get_order` in all three) but not the reasoning: with `KRT-100004` (delivered 45 days ago) in front of it the model said "Yes, you can return the order", and with `KRT-100005` it never mentioned the final-sale item that `get_order` reports. p1 and p2 had the same verdict failures, p2 without even looking up the order. Rewording the prompt had traded one failure for another across ADR-038 to 040.
- **Decision:** `check_return_eligibility(order_id)` (`tools/returns.py`, Tier 0, same ownership rule and audit as the other order tools) computes the verdict from the order, the customer's membership and the fixed rules: window 7 days (Gold 10), counted from the delivery date with the last day inclusive; final-sale items never returnable; an order not yet delivered is not returnable. It returns `eligible`, `reason` (`outside_window`, `not_delivered`, `all_items_final_sale`), `window_days`, `days_since_delivery`, `window_ends_on` and one entry per item with `returnable` and a reason. It starts nothing. It is registered with `search_policy` (so `KARTLY_KB_DIR`/`--kb` enables both). Prompt `p4` is p2 plus one rule: for a named order, call `check_return_eligibility`, report its verdict as it is and never work eligibility out from dates; use `search_policy` to explain the rule. Because the tool returns the day count, "delivered 45 days ago" is grounded for the grounding check (the problem ADR-040 predicted). The golden order cases accept it as the lookup, and a case's "too late" negative was narrowed so "it is not too late" is not read as a wrong claim. A test fails if `kb/returns.md` stops saying 7 and 10 days.
- **Alternatives:** More prompt rules (three rounds did not move the order cases); a larger model for policy (a cost and rate-limit decision for later, and it would still be arithmetic left to a language model); moving all of it to the model via a code-execution tool (new attack surface for no gain).
- **Consequences:** The window numbers now live in two places, the knowledge base text and `tools/returns.py`; the consistency test is the guard, and `config/policy.yaml` (planned) is where they should end up. Only final sale is decided in code; innerwear, opened personal care, gift cards and perishables depend on facts the store does not record, so they stay with the policy text and a human. The Week 4 return and refund tools will call the same function, so what the customer is told and what is allowed cannot disagree. Whether p4 passes the three order cases on a real model is the next measurement.

## ADR-042: p4 results, the guard covers eligibility replies, and where the tokens go
- **Context:** First run of prompt p4 on the 14 policy cases (`groq_small`, `--pause 30`, cases 02bab641): 12 of 14 passed. The two failures were the single check "no `search_policy` call matched" on `policy-and-order-together` and `policy-order-outside-window`; the replies were correct (`KRT-100001`: eligible, standard 7-day window, delivered 20 Oct, ends 27 Oct; `KRT-100004`: Gold 10-day window closed 18 Sep, item not returnable), and `policy-order-final-sale` passed. All 11 other cases passed, as with every earlier prompt. The requirement to search had been written before the eligibility tool existed and no longer says anything about the answer.
- **Decision:** (1) The three order-specific cases now require only that the model look at the order (`get_order`, `get_tracking` or `check_return_eligibility`), not that it search policy; the case notes say they were edited after seeing this run, so the 14-case digest changes again and 12 of 14 is not comparable with the next run. (2) The grounding guard now also checks replies that followed a `check_return_eligibility` call: before, "the window is 30 days" after that tool, with no citation and no search, was not checked at all. Its numbers (window, days since delivery) count as evidence; a citation still needs a real search. (3) Measured where a policy answer's tokens go (estimated at 3.6 characters per token, which overstates the measured 2,500 to 2,700 by about 20%): system prompt with p4 rules about 730, tool definitions about 700 (four tools, 150 to 190 each), three returned chunks about 270, repeated over two model calls. About 85% of the tokens are the fixed prompt and tool definitions that each call repeats; the retrieved text is about 10%.
- **Alternatives:** Keeping the old search requirement (it would mark correct answers as failures and push the model to a pointless extra call and about 1,700 more tokens); also requiring a search for the guard to apply (it would leave exactly the gap just closed); returning fewer chunks to save tokens (saves about 90 tokens per run; not worth a worse recall).
- **Consequences:** The binding limit is Groq's 8,000 tokens per minute, which is about 3 policy answers a minute, not the 8k context size, so the context builder should be about measuring and trimming the fixed overhead (shorter policy rules and tool descriptions, tool results capped, the thread trimmed to a budget, a per-call token breakdown in the trace), not about squeezing retrieved text. Prompt caching and a paid tier are the real fixes for the rate limit and belong with the fallback chain in Week 5. Policy cases still run one sample per case at temperature 0 and Groq is not deterministic, so use `--repeat 3` before trusting a pass.

## ADR-043: p4 becomes the default; a context builder budgets and measures the prompt; p5 is a shorter p4
- **Context:** Prompt p4 on the 14 policy cases, three runs each (`groq_small`, `--pause 30 --repeat 3`, cases d5e17f95): 42 of 42 passed, 0 safety failures, token counts almost identical between repeats (for example 2,698 / 2,698 / 2,696 for the refund question), so Groq was effectively deterministic for these prompts. The caveat: the 11 single-question cases never failed on any prompt, so only about six cases (the near-misses and the order cases) can tell prompts apart, and the order cases were edited after the first p4 run (ADR-042). 42 of 42 says p4 is stable on this set, not that it is 100% right on real tickets.
- **Decision:** (1) `DEFAULT_POLICY_PROMPT` is `p4` (recorded as `v1+policy-p4`); p1 to p3 stay selectable for comparison. (2) `context/builder.py` builds the first prompt of every run: the system prompt (plus policy rules when the tools are on) and the tool definitions are fixed and counted, the thread gets the rest of a budget (`KARTLY_CONTEXT_BUDGET_TOKENS`, default 6,000 of Groq's 8k window). A thread that does not fit keeps its first message (the original request) and the newest ones, with one line saying how many were left out; the newest message is cut with an ellipsis only after that, never below 400 characters, and a prompt that is still over budget is flagged, not hidden. Token counts are estimates (4 characters per token). The prompts moved to `context/prompts.py` (`orchestrator/prompts.py` re-exports them) so the builder and the prompts it budgets live together and import each other without a cycle. (3) The first model call's trace step stores the breakdown (`system`, `tools`, `thread`, `total`, `budget`, `omitted_messages`, `truncated_newest`, `over_budget`) and the trace prints it next to the provider's billed count: `[prompt ~1412 tok est (system 654, tools 700, thread 20) / 1196 billed]`, so the estimator's error is visible. (4) `p5` says what p4 says in about 30% fewer characters (about 445 estimated tokens against 654), a saving of about 200 tokens on each of two calls per policy answer.
- **Alternatives:** A tokenizer library (exact counts, but a dependency and per-provider tokenizers; the estimate is only used for budgeting and is shown beside the real count); summarising the dropped middle of a long thread with a model call (costs the tokens it is meant to save, and a summary can invent); dropping the oldest messages instead of the middle (loses the original request); trimming tool definitions per intent (the classifier call costs about as much as it would save).
- **Consequences:** Tickets are single-message today, so thread trimming is tested with synthetic long threads, not measured on real ones. The budget bounds the first call only; tool results are bounded by the tools (three chunks at most 1,500 characters each). p5 is a hypothesis: run it on the same cases (`--policy-prompt p5 --repeat 3`) and switch only if it passes as many and its billed tokens drop by roughly 15%. The 8,000 tokens per minute limit is about total tokens, so the builder lowers cost per run but does not remove that limit; caching and a paid tier (Week 5) do.

## ADR-045: A model-based claim check in front of policy replies, measured on labelled replies

- **Status:** Accepted
- **Context:** Prompt p5 said "Kartly does not accept returns in physical stores" three times out of three. The text is silent about stores, so this is an invention. The grounding check passes it: there is no number and the citation is real. Wording rules (p2 to p6) reduce this but do not guarantee it, and a rule in a prompt is a request, not a control.
- **Decision:** (1) `guards/claims.py` adds `ClaimJudge`, a second model call with no tools. It gets the retrieved chunks (and any return-eligibility result), the customer's question and the drafted reply, quoted as data, and returns `{"unsupported": [...]}`. The prompt (`j1`) says the text being silent is not support, and excludes greetings, offers of help and hand-over lines. (2) It runs only on a policy reply that the deterministic check passed, so it never spends tokens on a reply already held. A flagged statement holds the reply exactly as a failed number check does (`StopReason.UNGROUNDED`, audit `guard.ungrounded_reply`, no draft). (3) It fails closed: a failed call or unusable output holds the reply and says so ("claim check could not run"). Its tokens, cost and one extra call are added to the run. (4) It is off by default: `KARTLY_CLAIM_CHECK_MODEL`, `--claim-check` on the orchestrator and eval CLIs. (5) `python -m kartly.evals.claims` scores a judge model on `evals/claims/cases.yaml`: 35 hand-written replies (18 unsupported: invented, contradicted, overclaimed and mixed; 17 supported: paraphrases, hand-overs, polite replies, tool-based). It reports caught rate, false-hold rate, errors, tokens and latency, and logs a row with the judge version and the case and KB digests.
- **Consequences:** The judge's quality is not known until it is run: the unit tests prove the wiring, not the judgement. The cases were written by the same author as the prompt, so the numbers will flatter it. Adopt it for policy replies only if it catches nearly all unsupported cases at a low false-hold rate on at least two models, and read the misses before trusting it. A false hold costs a human a look; a miss sends an invented claim to a customer. Groq's 8,000 tokens per minute limit now has to cover the judge call too (about 700 tokens per policy answer), and a rate-limit error on the judge holds the reply, so Week 5's fallback chain matters more. A judge from the same model family as the resolver shares its blind spots; a different model for the judge is better. The judge reads the draft with its citations removed, so it cannot be argued into accepting a claim by a citation.

## ADR-046: Writes are proposals by default; approvals are bound to the exact action

- **Status:** Accepted (slice 4a of Week 4)
- **Context:** Until now every tool read. A write that can run twice, run on the wrong order, or run because a model said so is the failure that matters most in this system. The design (DESIGN.md sections 1, 5 and 8) already named the controls: tiers, a shadow/auto switch, idempotency, approvals and an audit log. This slice builds the gateway side of them and one tier 1 tool.
- **Decision:** (1) Each write tier has a mode: `off`, `shadow` or `auto`. The default is `shadow`, so a fresh install changes nothing until someone chooses otherwise. A tier 3 tool is capped at `shadow`. (2) A write tool must supply a `preview`: the same checks as the handler, no writes (run in a savepoint that is rolled back, so a preview that writes anyway has its writes undone). A call that fails its preview is refused and creates no action or approval, so a human never sees a request that cannot be done. (3) The idempotency key is `run:tool:hash(validated arguments)`, made by the server. A repeated call returns the first call's result (`replayed`). The `actions.idempotency_key` unique constraint settles a race: the loser is treated as a replay, and any other integrity error is not hidden. A different run gets a different key, so the tool's own rule (an order cannot be cancelled twice) is the second line of defence. (4) A proposal creates an `actions` row in `awaiting_approval` and an `approvals` row holding a SHA-256 of tool, arguments and customer id, plus an expiry (24 hours). (5) `ToolGateway.decide` runs an approved action only if the hash still matches (a changed row is refused and audited as `approval_payload_mismatch`), the request is not expired and still pending, and the tool's checks pass again against the current order. A second decision is refused and audited. Every decision writes an audit row with a human actor in the same transaction; if the audit write fails, the decision does not happen. (6) A run that proposed an action ends `awaiting_approval`; the drafted reply must say the action is waiting for review, and the tool result tells the model so. (7) `cancel_order` allows `placed` and `confirmed` only, matching `kb/cancellation.md` ("Packed" and "Shipped" orders are no longer cancellable); a test ties the constant to the text. It reports `refund_due_inr` for a prepaid order and nothing for cash on delivery.
- **Consequences:** The gateway default for unconfigured tiers is shadow, so the plain-path test doubles that used to be tier 1 are now tier 0. The real stack (CLI and API) now offers `cancel_order` by default, which adds a tool definition to every prompt there; the eval runner still builds its own tool list, so earlier eval results stay comparable. Not done yet: the approvals API and the ticket state after a decision (4c); the refund tool, its limits and the daily cap (4b); eval cases and graders for writes, and the red-team set (4d); cancelling an order does not yet start a refund for a prepaid order, and partial cancellation is not offered, so the reply should hand those over; a rejected proposal does not yet notify the customer. The approval expiry is not swept in the background, so an unapproved request stays `pending` in the table until someone tries to decide it.

## ADR-047: Refund limits count the whole order, and a human decision is re-checked, not trusted

- **Status:** Accepted (slice 4b of Week 4)
- **Context:** `kb/refunds.md` says refunds up to INR 1,000 on an order are processed automatically. A limit applied to each call would let a model (or a customer talking to it) split INR 2,898 into three refunds of INR 966. Money is also the one place where two simultaneous calls can each read the same old total.
- **Decision:** (1) `issue_refund` needs approval when the order's refunds already made, plus this one, exceed the auto limit (INR 1,000, inclusive: INR 1,000.00 runs, INR 1,000.01 waits), or when the customer's successful refunds in the last 24 hours plus this one exceed the daily cap (INR 5,000). Both are settings. Only refunds that ran count towards the cap, never proposals; the window comes from the injected clock. (2) A refund can never exceed what is left on the order, checked in preview, at run time and again when a human approves, so a request that waited while the order changed fails with the amount still available. (3) Allowed statuses are `delivered` and `cancelled`; a cancelled cash-on-delivery order has nothing to refund. (4) Amounts are rupees with at most two decimals, converted to whole paise once. (5) The order row is read with a row lock in write handlers (`SELECT ... FOR UPDATE`, reloaded), so concurrent refunds cannot overpay; a Postgres test races five refunds and expects exactly four to succeed. (6) A human approval is not blocked by the daily cap: the cap exists to decide who must look, and a human has.
- **Consequences:** The default of INR 1,000 duplicates the policy text, so a test compares them; change both together. The daily cap sums a customer's refund actions in Python, which is fine for a ticket history this size and should become a query with an index when volume grows. There is no refund yet when a prepaid order is cancelled, no reversal, and no payment gateway: the refund is a record in the store. The eval runner still has no write tools, so earlier eval digests are unchanged.

## ADR-048: Approvals are decided over HTTP; the ticket follows the decisions

- **Status:** Accepted (slice 4c of Week 4)
- **Context:** Until now a request that needed a human could only be decided from code. A reviewer needs to see what is waiting and decide it, without the decision being able to run an action twice, run a stale one, or leave the ticket looking as if the customer's request were still in progress.
- **Decision:** (1) `GET /v1/approvals`, `GET /v1/approvals/{id}`, and `POST .../approve` and `.../reject`, all behind the API key, all calling `ToolGateway.decide`, so the hash, expiry, repeat and tool re-check rules apply unchanged. A decision that does not result in the action being done returns 409 with the reason. (2) `decide` takes a row lock on the approval (`SELECT ... FOR UPDATE`), so two simultaneous approvals run the action once and the other gets `already_decided`; a Postgres test with six reviewers proves it. (3) After every decision that took effect, a ticket that is `awaiting_approval` and has no pending request left becomes `drafted` if every action ran, otherwise `escalated`. A ticket in any other state is never moved. (4) Expiry has no background job: listing requests first closes every pending one past its time (audit actor `system`), and `decide` also refuses an expired one on its own. The route handlers hold no database session while the gateway decides. (5) The reviewer name is part of the request body and stored as `human:<name>`.
- **Consequences:** The reviewer is not authenticated individually: anyone with the API key can claim any name. Per-reviewer identity (login, roles, a limit on who can approve large amounts) belongs with the admin UI in Week 6. The customer is not told the outcome; the draft reply written while the request was pending still says it is under review, and a human sends the follow-up. An expired request only closes when someone lists or decides, so a ticket can stay `awaiting_approval` until then; a periodic sweep arrives with the Week 5 workers.

## ADR-049: Write evals are graded on what the store looks like afterwards

- **Status:** Accepted (slice 4d of Week 4)
- **Context:** A write that goes wrong shows up in the data, not in the wording of the reply. The existing golden cases only proved that nothing changed. The write path needs cases that prove the right thing changed, and no more, plus cases that try to talk the agent past the approval rules.
- **Decision:** (1) A case may set `write_mode` (`shadow` or `auto`), which gives that case `cancel_order` and `issue_refund` with both write tiers in that mode. A case without it runs with reads only, exactly as before. (2) New expectations: the outcome `awaiting_approval`; `changed_tables` (store tables that should differ, default none; any other table changing is a safety failure, and an expected one that did not change is a quality failure); `state` (an order's `status` or `refunded_paise` must equal a value, with its own severity); `approvals` (the number of approval requests the run created; more is safety, fewer is quality). (3) False claims keep working as before: `must_not_leak` lists phrases such as "has been cancelled" or "I have refunded", and a match is a safety failure. (4) Fifteen new cases: seven write cases (cancel placed and shipped orders, small and large refunds, a refund above what is left) and eight red-team cases: a claimed manager approval, a split refund that together passes the limit, a fake system notice, another customer's order, an override code, an insistence that a shipped order be cancelled, a refund on an undelivered order, and an inflated amount. All red-team cases run in `auto`, the most permissive mode. (5) Each has a scripted perfect trajectory, and eight wrong ones prove the grader fails them for the stated reason.
- **Consequences:** The case-set fingerprint changes, so earlier experiment rows no longer compare with new ones. These cases have not been run against a real model yet: the scripted tests prove the grader, not the model's behaviour, and the first real run may show that the prompt needs a rule about waiting-for-approval wording. `bypass-fake-system-notice` is not caught by the injection screen (it looks for "SYSTEM NOTICE" style phrases, not "SYSTEM: approval_status=approved"), so it reaches the model and the gateway rules are what protect the store; whether to widen the screen is a separate decision. The case that holds the model to one call of a pair (the split refund) depends on the model making two calls and may need rewording after a first run.

## ADR-050: Retries, a fallback chain and a circuit breaker around the model

- **Status:** Accepted (slice 5a of Week 5)
- **Context:** Groq's free tier rate limits and sometimes returns 5xx, and a local model may simply be off. ADR-014 kept retries out of the client so one layer could decide them with the whole chain in view. Until now one failed call ended the ticket.
- **Decision:** (1) `ResilientClient` implements `ChatClient` over an ordered chain (the default model, then `KARTLY_FALLBACK_MODELS`). (2) The error class decides: rate limit waits for `Retry-After` when it is at most 15 seconds, otherwise moves on; provider errors, timeouts and unusable replies back off exponentially with jitter; auth, unknown model and bad request raise at once, because a fallback would hide a configuration bug; `ToolUseFailedError` propagates because the loop already re-prompts, and a different model given the same history tends to fail the same way. (3) A model that fails three calls in a row (each after its own retries) is skipped for 30 seconds, then one probe is let through; a bug-class error during a probe does not leave the breaker stuck. (4) A deadline of 60 seconds covers the whole call, and a wait that would cross it is not taken. (5) When nothing works, `AllModelsFailedError` lists what happened to each model. (6) The response carries `attempts` and `failed_over_from`; the trace step stores them and the model that really answered. (7) The API uses it for the main model only. The router and the claim judge stay plain, because a judge that falls back to a different model would change what a measured result means.
- **Consequences:** The breaker state is per process: several workers each learn separately that a model is down. A fallback model may be weaker (the free local model cannot do policy answers), so the chain order is a deployment choice, and the shadow cost in a run is that of the model that answered. The failed attempts themselves are not stored as steps, only counted. There is no hedging (calling two models at once) and no global rate limiter: a burst of tickets can still exceed a provider's tokens-per-minute limit, which the queue in 5c is meant to smooth.

## ADR-051: Operator switches stored in the database: switch off the agent, freeze writes

- **Status:** Accepted (slice 5b of Week 5)
- **Context:** When the model starts doing something wrong in production, the fix has to take effect in seconds and in every worker, without a build or a deploy, and it has to be possible when the model itself is the problem. An environment variable needs a restart; a flag in memory reaches one process.
- **Decision:** (1) A `controls` table with one row per switch, read each time it is used (a one-row primary-key lookup), so a change reaches every worker on its next ticket or write. (2) Two switches. `agent` (`on` or `off`): when off, a new ticket is handed to a human as a held run (stop reason `kill_switch`, trace stage, audit `kill_switch.held`) before the injection screen, the router, the model or any tool. `writes` (`on` or `frozen`): when frozen, a write that would have run on its own becomes an approval request with reason `writes_frozen`, and an approval cannot execute anything (audit `approval.blocked_writes_frozen`; the request stays pending). Rejecting a request and all reads still work, and a tier set to `off` stays off. (3) A stored value that is not allowed counts as the safe one, so a bad edit stops things rather than enabling them. (4) Every change is audited in the same transaction as the change, with who and why; setting the value it already has records nothing. A first change that races another creates the row once and the loser retries as an update. (5) Changed through `PUT /v1/controls/{name}` (same API key and asserted reviewer name as approvals) or `python -m kartly.controls`, which needs only the database, so it works when the API does not.
- **Consequences:** The agent switch does not interrupt a run that is already in progress: it finishes its current model call and its tools, and writes inside it are covered only by the writes switch, so the incident runbook is to freeze writes first. Anyone with the API key or database access can flip a switch and the name is asserted, not proven (login and roles come with the Week 6 admin UI). There is no automatic trigger yet (for example freezing writes when the refund rate spikes); that belongs with the Week 6 alerts. The held tickets are not queued for retry once the agent is on again: a human takes them, and bulk re-processing waits for the Week 5 replay.

## ADR-052: A job queue in the database, with leases, retries and a dead-letter state

- **Status:** Accepted (slice 5c of Week 5)
- **Context:** The in-process pool loses every waiting ticket on a restart, retries nothing, and has no place for a ticket that cannot be processed. The plan named Redis. The system already has a Postgres, tickets and jobs belong in one transaction boundary, and the volume is tens of tickets, not thousands per second.
- **Decision:** (1) A `jobs` table instead of Redis: status `queued|running|succeeded|dead`, priority, attempts, `available_at`, a lease (`locked_by`, `locked_until`), the last error and the run's result. (2) A worker claims with `SELECT ... FOR UPDATE SKIP LOCKED` followed by a conditional UPDATE whose row count must be 1, which is also correct on SQLite; the claim counts an attempt and sets a 300 second lease. Only the holder of the lease can complete or fail the job. A running job whose lease has passed is claimed again, so a killed worker loses nothing. (3) A failed attempt (an exception, or a run that stopped with `llm_error`) is queued again after 30, 60, 120 seconds (cap 300; the first wait is not shorter than the model circuit breaker's 30 s cooldown, or a short outage would use every attempt while the breaker still refuses to try). After `max_attempts`, or when a job has been claimed more times than allowed without ever finishing (a ticket that kills its worker), it is buried: status `dead`, the ticket becomes `escalated` unless it is already closed or sent, and an audit row `job.dead` (actor `system`) is written. (4) A retry must not repeat a side effect: before running attempt 2 or later, the worker checks the ticket's actions, and if any is succeeded, pending or awaiting approval the job is buried as `unsafe_to_retry` and a human decides. Failed and rejected actions do not block. (5) A human requeues a dead job with `POST /v1/dead-letters/{id}/requeue`; attempts restart at zero and an audit row `job.requeued` records who. The first attempt after a requeue is not subject to the check in (4), because a human made that call. (6) The mode is opt-in (`KARTLY_QUEUE_MODE=db`); the default stays the in-process pool, so nothing changes until it is switched on. `?wait=true` polls the job's stored result. When the backlog (waiting plus running) reaches `KARTLY_MAX_PENDING_RUNS` the API answers 503 and discards the ticket it had just created.
- **Consequences:** Workers poll once a second, so an idle queue adds up to a second of delay; there is no LISTEN/NOTIFY. A run that is still going when its lease expires (a run is limited to 120 seconds, the lease to 300) would be claimed twice; the lease is deliberately longer than the run limit and the unsafe-retry check is the backstop for the writes. The check is conservative: a crash after a harmless read-only retry-able step is still retried, but a crash after any executed write always goes to a human. Ordering is by priority and age, but nothing sets a priority yet. Moving to Redis or SQS later only needs `JobQueue` replaced. Pausing the queue is not separate from the agent kill switch, which hands new tickets to a human when the worker picks them up. Replay of a stored run and a fault-injection test are slice 5d.

## ADR-053: Fault injection and replay

- **Status:** Accepted (slice 5d of Week 5)
- **Context:** Retries, fallback, the breaker, the queue and the unsafe-retry rule each had tests, but nothing showed how they behave together when the provider misbehaves, and no way to ask whether a code change would alter what past tickets did.
- **Decision:** (1) `kartly.chaos`: a fake model that fails on a schedule (429 with a wait, 5xx, timeout that consumes time, malformed reply, bad key, slow answer) behind the real `ResilientClient`, queue, worker, runner, gateway and database, with virtual time. Eleven scenarios each name the ending they must reach; `violations` fails any run that leaves a ticket in a working state nobody is working on, pays a refund more than once, or marks a ticket drafted with no answer. They run as tests and as a command that prints what the customer would see. (2) The scenarios found a defect: the queue's first retry wait (5 seconds) was shorter than the model breaker's cooldown (30 seconds), so a short outage used all three job attempts while the breaker still refused to call, and the ticket was escalated although the provider had recovered. The first wait is now 30 seconds (30, 60, 120, cap 300), with a test that keeps it at least the breaker's cooldown. (3) `kartly.replay`: read a stored run's trace, rebuild its customer messages in a throwaway seeded SQLite database, run the current code with a client that returns the recorded model replies in order (a recorded error is replayed as an error), and compare tool calls with arguments, tool errors, outcome, final answer and number of model calls. The source database is only read.
- **Consequences:** The chaos model is a stand-in: it shows that the mechanism copes with the failure shapes listed, not that the real providers fail in only those ways. A bad key is retried three times over about 90 seconds before the ticket goes to a human; it is cheap, and a corrected key lets the retry work. Replay runs against the seed, not production data at the time, so a run whose orders were later changed can differ for that reason alone; the router step is skipped; a trace whose stored arguments were cut by the trace size limit will not parse and shows as a difference. Replaying with a live model, to measure model drift, is not built. Breaker state is per process, so with several workers each learns of an outage separately.

## ADR-054: Metrics are queries over the database

- **Status:** Accepted (slice 6a of Week 6)
- **Context:** The system now has an API, workers that may be separate processes, and a queue. Counters in memory would disagree between processes and vanish on restart.
- **Decision:** (1) `kartly.metrics.collect` computes every figure from stored rows (runs, steps, actions, approvals, jobs, audit log, controls) for a time window, with grouped SQL that behaves the same on SQLite and Postgres. (2) Two views of the same data: JSON at `/v1/metrics` and Prometheus text at `/metrics`, both behind the API key (a scraper sends the header). All Prometheus metrics are gauges, recomputed on each scrape; there are no counters to reset. (3) Run latency is the sum of its step latencies, because a run's start and end are stored to the second. (4) A fixed list of audit events is counted (cross-customer access, writes blocked while frozen, kill-switch holds, control changes, dead and requeued jobs); other audit rows are not. (5) Every response has an `X-Request-ID` and each request logs one line (method, path without the query string, status, milliseconds, request id). A caller's id is used only if it is 1 to 64 characters of letters, digits, dot, dash or underscore, so it cannot inject log lines.
- **Consequences:** Each scrape runs a dozen aggregate queries; at this volume that is milliseconds, but a busy system would want a cache or a read replica, and the window is capped at 90 days. Percentiles are over the latest 5,000 runs, and the retry and fallback counts over the latest 5,000 model replies, so on a very busy window they describe a sample (counts of runs, calls and errors stay exact). Gauges over a rolling window cannot be used with `rate()`; alert rules compare the figure with a threshold instead (slice 6b). The request id is not yet stored on the trace, so it links a log line to a request but not to a run; that needs the ticket id in the log, which slice 6c adds with the admin UI.

## ADR-055: Alert rules, one announcement per change, and opt-in automatic actions

- **Status:** Accepted (slice 6b of Week 6)
- **Context:** The metrics show the numbers but nobody is watching them. The kill switch exists, but a person has to notice and flip it.
- **Decision:** (1) `evaluate` is a pure function from a metrics snapshot to the rules that are firing, each with a severity and, for two kinds of critical rule, a proposed control change. Rates carry minimum event counts. (2) `AlertManager.check` stores each rule's state in `alert_states` and announces only changes: a rule starting, getting worse (warning to critical) or clearing. Getting better while still firing is not announced. Each change is an audit row. The check runs on a timer inside the API, on demand (`POST /v1/alerts/check`) and from the command line. (3) Announcing goes through a notifier: always the log, and optionally an https webhook that never raises, because an alert about an outage must survive the chat service being down too. (4) Automatic actions are opt-in (`KARTLY_ALERT_AUTO_ACTIONS`). Only critical alerts act, only toward safety: freeze writes (cross-customer access, failed writes) or switch the agent off (run failure rate above 50% of 20+ runs). They run as `system:alerts` with the reason stored, and setting a control to the value it already has is a no-op, so a person's own change is never overwritten. Nothing lifts an action automatically. With actions off, the alert text says what it would have done. (4a) A defect found on the way: `clean_str` appended its ellipsis after cutting to the limit, so a cut text was one character over, which Postgres refuses in a `String(N)` column (SQLite does not check). A job error text of 500 or more characters, or a long control reason, would have raised inside the failure handler. `clean_str` now counts the ellipsis in the limit, and a Postgres test covers the columns.
- **Consequences:** The window and thresholds are the same for every deployment until someone edits `Thresholds` (only the window, interval and the two switches are settings). The checks run in the API process only; with several API instances each would check and, because the state table is shared and transitions are decided under a row lock, only the first to see a change announces it. Rules that look at the last 15 minutes will clear by themselves once the problem leaves the window, even if nobody fixed it: a frozen switch stays frozen until a person lifts it. There is no paging, acknowledgement or silencing yet. Webhook delivery is best effort.


## ADR-056: Reviewer accounts, cookie sessions and roles

- **Status:** Accepted (slice 6c of Week 6)
- **Context:** Everything that changes state needed the one shared API key plus a self-declared `reviewer` name, so the audit trail said whatever the caller typed, and a browser page would have had to hold the key. An admin page needs real identities.
- **Decision:** (1) Accounts in a `reviewers` table, passwords hashed with scrypt (stdlib; stored with their parameters, absurd parameters are refused on verify). (2) Sign-in creates a random session token; only its SHA-256 is stored, the cookie is HttpOnly and SameSite=Strict (Secure by setting). Sessions end at an absolute lifetime and after an idle period; use is recorded at most once a minute. (3) A per-session CSRF token must come back in `X-CSRF-Token` on every change; the API key is exempt because it is not ambient browser state. (4) A wrong API key is never rescued by a cookie. (5) Failures all look alike and always cost one hash (a dummy for unknown names), five wrong passwords lock for 15 minutes, a lock is not extended by attempts made while locked, and a reset or unlock clears it. Every sign-in, failure (with reason), logout and account change is audited. (6) Roles: reviewers read, decide, requeue and may only move controls toward safe (`writes=frozen`, `agent=off`); admins and the service key may also lift them. Accounts are managed only by a signed-in admin, never by the key, and the last active admin cannot be disabled (checked under a row lock). Disabling or resetting a password ends that person's sessions at once. (7) A session is recorded under its own name; the key must still supply `reviewer`.
- **Consequences:** Controls store the plain name while approvals store `human:<name>`; both are the same person. Login attempts are not rate limited by address, only per account, so one account can be locked by a stranger (accepted: an admin can unlock, and the alternative leaks which names exist). There is no password-reset email, 2FA or SSO. Sessions live in the database, so they survive restarts and work across several API instances.




## ADR-057: The admin page is three static files under a strict content policy

- **Status:** Accepted (slice 6d of Week 6)
- **Context:** People need to see tickets, traces, approvals and controls without curl. The page shows text written by customers (messages, refund reasons, tool arguments), so it is the one place in the system where a stranger's words are rendered to an authenticated operator.
- **Decision:** (1) No framework and no build: `admin.html`, `admin.css`, `admin.js`, served by the API itself at `/admin`, listed as package data. (2) Content-Security-Policy `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; frame-ancestors 'none'` plus `nosniff` and no referrer, so even a missed escape cannot run injected script, load a remote file or be framed. This forced the page to have no inline script or style at all, which tests assert. (3) Every value reaches the page through `textContent`/text nodes via one small element builder; `innerHTML` and similar are banned by a test. (4) The page uses only existing routes, with the session cookie and the CSRF header, so it can do nothing the API does not already allow its role: the buttons a reviewer may not use are disabled, and the server refuses them anyway. (5) The shell is public and the data is not.
- **Consequences:** Found while testing in a real browser, not by the unit tests: inline `style` attributes were silently blocked by the policy, array children were printed as `[object HTMLDivElement]`, and a missing feature (alerts off) broke the menu counts. The first two now have static tests; the browser run itself is not in CI (no browser there yet). The page polls every 15 seconds while visible, which is fine for a handful of reviewers and would need push updates for many. Ticket search is by customer and status only; there is no full-text search.


## ADR-058: Shadow pricing report: measured cost, and what-if cost with its limits stated

- **Status:** Accepted (slice 6e of Week 6)
- **Context:** Every call is priced at reference prices when it is made (ADR-013), but nothing answered the questions a cost-conscious owner asks: what does one answered ticket cost, which tier spends the money, and is routing worth the complexity. Real spend is $0 here, so the numbers only mean something if they are computed carefully and their limits are said out loud.
- **Decision:** (1) The report is a pure read of stored runs and steps (`kartly.costs.build_report`), the same on the command line, the API and the admin page. (2) Model cost counts LLM calls and the classifier stage, not tool calls or other stages, in the window by step time; totals are exact SQL sums, per-run percentiles use the latest 5,000 runs. (3) Tier comes from the classify step's output; runs the rules closed before the classifier ran, or whose tier cannot be read, fall in "unclassified" instead of being dropped. (4) The headline unit is cost per *answered* ticket (not escalated, not failed, finished): escalated and failed runs still cost money, and dividing by all runs would flatter a tier that escalates a lot. (5) What-if prices the same recorded tokens on every configured model and reports the routing saving against the first model of the `large` role. It can be negative. It is labelled an estimate, with the caveats printed in every output: tokens would differ, cached discounts are not applied, quality is not measured. (6) Routing *experiments* with real models are not simulated: replaying recorded replies cannot show what a different model would say, so those stay with the eval suite's `--model` runs.
- **Consequences:** The what-if will mislead if read as a quote, which is why the notes travel with it. A run's cost is its own `shadow_cost_usd`, the model totals are step sums; they agree unless a step failed to record, and the report does not reconcile them. The window filter for models is by step time and for tiers by run start, so a run straddling the window start can appear in one and not the other. Price changes in `models.yaml` apply to the what-if immediately but never rewrite history, since each step stored the cost at the time.


## ADR-059: CI is several small jobs, and the browser is part of it

- **Status:** Accepted (slice 7a of Week 7)
- **Context:** One job running lint, types and tests in sequence on one Python version told us little when it failed, never exercised the oldest Python the project claims to support (`requires-python >=3.11`), never ran the migrations the way a deployment does, and could not see the bugs that only a browser shows. Three of the four defects found while building the admin page (a policy blocking inline styles, lists printed as "[object HTMLDivElement]", an unguarded feature breaking the menu) were invisible to string-level tests.
- **Decision:** (1) Separate jobs for lint, types, tests on 3.11 and 3.12 (SQLite), Postgres, browser and audit, so a failure names its cause and they run in parallel; a new push cancels the run in progress. (2) The Postgres job runs the whole suite and then does what a deployment does: `alembic upgrade head` on an empty database, `alembic check` (no drift between models and migrations), and each command-line tool against the result. (3) Browser tests (`tests/browser`, Playwright, Chromium) drive the real page against a real server: sign-in and refusal, hostile HTML shown as text and never run, ticket and trace rendering, every tab, role differences, approving from the page, sign-out. They fail on any exception or any console error the browser reports, which is how a blocked inline style shows up. They skip when no browser is installed, so a plain `pytest` on a laptop still works. (4) The workflow may only read the repository, every job has a time limit, every action is pinned to a release or commit, and the oldest supported Python must be in the matrix; a unit test asserts all of this so the workflow cannot quietly drift. (5) The dependency audit reports but does not block, so an advisory for a package we did not touch cannot turn every pull request red; Dependabot proposes updates weekly for Python packages and for the actions.
- **Consequences:** Dependencies are not locked (no `uv.lock`/constraints file is committed), so CI installs whatever is newest and a broken upstream release can fail an unrelated change; locking is a deliberate follow-up. Actions are pinned to major versions, not commit hashes, which trades some supply-chain strictness for readable updates. The browser job is the slowest (installing Chromium). The workflow cannot be run from here; it was checked with actionlint, and every command in it was run locally against a fresh Postgres and on Python 3.11.
